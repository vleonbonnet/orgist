#+TITLE: Orgist Phase 2 — Org as Source of Truth
#+STARTUP: overview

Design exploration for collapsing Todoist-mirror files into ordinary notes files: org becomes the source of truth and Todoist a projection of the tasks inside them.  Status: exploration — nothing described here is built.

* Summary

- *Phase 1 — mirror mode (today).*  Todoist is the source of truth.  Orgist owns one file per root project under =orgist-base-dir=, and everything in those files also exists in Todoist.  A reset can delete them and resync: Todoist is the backup.
- *Phase 2 — overlay mode.*  The user's notes files are the source of truth. Todoist shows the TODO headings inside them, arranged under the org category tree.  Notes outside tasks never leave org; a task's own body keeps syncing as its description, as today.
- The shift inverts ownership of /content/, not of /task fields/.  Both sides still edit titles, dates and completion; what changes is that Todoist can no longer destroy or restructure notes outside tasks.  A task deleted on either side is deleted on both; the destruction journal keeps it recoverable.
- As soon as a file holds content Todoist lacks, the implicit backup is gone. The first milestone is therefore a safety net (file history, destruction journal, blast-radius guards, safe reset), shipped in mirror mode where it already protects today's files.
- Mirror stays the default.  Overlay is opt-in per Todoist project, so both modes coexist during migration and for other users of the package.

* What "source of truth" means

Authority is split per aspect rather than per side:

| Aspect                                           | Owner (overlay)     | Consequence                                              |
|--------------------------------------------------+---------------------+----------------------------------------------------------|
| Existence of notes outside tasks                 | org                 | never touched by a remote change                         |
| Existence of tasks                               | shared              | delete means delete, on both sides; journaled            |
| Tree structure and placement                     | org                 | remote moves are proposals, reviewed                     |
| Which headings are exposed                       | org                 | scope rules and tags decide                              |
| Task fields (title, state, priority, dates, ...) | shared              | three-way merge on the snapshot; org wins true conflicts |
| Comments                                         | shared, append-only | logbook notes \leftrightarrow comments, as today                       |
| Task body \leftrightarrow description                          | shared              | synced as today, same three-way merge                    |
| Notes outside tasks                              | org                 | never exported                                           |

Rows 10, 16 and 17 are live in mirror mode today.  Row 10: a large pull landing while a mirror buffer has unsaved edits is later overwritten by the save, and the snapshot then describes remote state the file no longer has.  Row 16: any task that got an org-id (=org-store-link=, capture, org-linker) before its first push loses it, and links to it dangle.  Row 17: the description sync is one-way below the first child heading.

* M0 — Safety net, before any overlay code

In mirror mode every managed file is recoverable from Todoist.  Overlay files hold notes that exist nowhere else.  Each past incident — drift baking (2026-07), element-cache skew (2026-08-12), region smear (2026-08-16), duplicate heading from a stale marker (2026-09-12) — was a sync pass mutating user-visible buffers in a way nobody noticed immediately.  Detection and reversibility must exist before the blast radius grows to include notes.

** Close the live loss paths

Rows 16 and 17 lose data in mirror mode today, so they are fixed first, each with a regression test: a heading keeps a pre-existing org-id (see Identity), and a task's non-task child headings are part of its description in both directions (see Inbound).

** Layer 1 — File history

- *Pre-cycle commit.*  Before the first mutation of a sync cycle, commit the current content of every file the cycle may touch.  This records the user's own edits since the last cycle as a separate commit.
- *Post-cycle commit.*  After the cycle, commit again.  The message is the cycle summary: pulled events with IDs, commands sent, results.
- History then alternates "local edits" and "sync" commits, and =git log -p= answers "what did the 07:22 pull do to this file" exactly — the forensics every incident so far needed by hand.
- Shadow repository: separate =--git-dir= per root (=<state>/history.git=, work-tree = the root), so a user's own repository is never touched. =core.autocrlf=false=, synchronous =call-process=.
- State files (snapshots, stamps, token) are committed too, for forensics only: a restore brings back files, never state (see Restore below).
- Fallback when =git= is missing: content-addressed copies =<state>/history/<file>/<time>-<sha1>.org=, deduplicated by hash, with retention (everything for 14 days, one per day for a year).

** Layer 2 — Destruction journal

Every destructive primitive appends an entry to =<state>/journal.org=: delete subtree, replace body, delete file, transplant, and overwrite of a local field with a remote value.  An entry holds time, cycle, file, outline path, ID, reason (remote event or command), and the removed text verbatim in a src block.

The journal is an org file, so it is greppable and restorable by copy-paste; =M-x orgist-journal= browses it and re-inserts an entry.  This gives subtree-level restore without rolling back whole files, which would also discard unrelated edits.

** Layer 3 — Blast-radius guards

- *Per event.*  Each mutation primitive declares the region it may touch (the target subtree).  An =after-change-functions= recorder tracks the extent of changes while it runs; a change outside the declared region aborts the cycle.  This would have stopped the region smear at its first heading.
- *Per cycle.*  Before saving, compare each file's heading count and size to the pre-cycle commit.  Heading removals without matching journal entries, or shrinkage above a threshold, abort the cycle: buffers are restored from the pre-cycle commit, the sync token is not advanced, and the user is warned.  This generalizes the existing "snapshot count dropped by half" guard from state to content.
- *ID invariant.*  IDs after a pull = IDs before + added − journaled deletions.  A duplicate ID is an error, never "first match wins".

** Layer 4 — Safe reset

- =orgist-reset-state= drops snapshots, stamps and token and rebuilds them from remote ([[id:4299b593-37f9-4f85-a99c-afbdaff627eb][M2 — Rebuild-and-validate from remote]]).  It never touches files.
- File deletion remains only in mirror mode, only for files inside =orgist-base-dir= that carry the mirror marker (=TODOIST-PROJECT= property and the =todoist= filetag), and only after a history commit.
- Refuse outright when the base directory is =~=, a version-control root, or contains unmarked =.org= files.

** Layer 5 — Outside orgist

Filesystem snapshots (e.g. ZFS on a NAS) are the last line of defence. Orgist cannot rely on them, but the documentation should recommend them.

** Restore

- =orgist-history=: list cycles; ediff a file against its pre-cycle version.
- =orgist-undo-cycle=: restore files to the pre-cycle commit, then rebuild snapshots from remote, so any remote change that cycle applied reappears as a pending diff (review, push or re-pull) instead of vanishing.  The token or snapshots are never rolled back on their own.

* Overlay model

** Vocabulary

- *Overlay file* — a notes file bound to one Todoist project.
- *Linked heading* — a heading bound to a Todoist task, section or project through its ID (see Identity).
- *Exposed task* — a TODO heading in scope, linked or about to be.
- *Container* — a non-task heading that is an ancestor of an exposed task.
- *Landing zone* — where remotely created tasks without a bound parent land.
- *Projection* — the deterministic function from the org tree to the Todoist tree.

** Example

#+begin_example
#+TITLE: Home
#+TODOIST_PROJECT: 2203306141

,* TODO Renew home insurance            ← top-level task: in the project, no section
:PROPERTIES:
:ID:       6X9bTt4KqWm2Lr7Z      ← Todoist ID, as today
:END:

,* Garden
:PROPERTIES:
:ID:       0f8c2d8e-…            ← org-id other notes link to: kept
:TODOIST_ID: 6c2Hq8RvPw3Xk9Fm    ← so the section ID goes here
:END:
Soil test results, plant list, supplier contacts…

,** Irrigation
Zone map and valve schedule…

:PROPERTIES:
:ID:       6X7fQ9mRw2cVp8Hh
:END:
Buy the 1" anti-siphon model; the old one is in the shed.   ← description

,**** Parts list                        ← inside a task: part of its description

** Registration and binding

- *Two keys.*  A file is overlay only when it is listed (directly or via a root) in =orgist-overlay-files= *and* contains =#+TODOIST_PROJECT: <project-id>=.  A stray keyword or a misconfigured list alone activates nothing.
- The keyword is deliberately distinct from mirror's =TODOIST-PROJECT= property, so =maybe-enable-orgist= never enables mirror behaviour on a notes file.
- Bound by project ID, not name: renames on either side keep the binding, and the keyword travels with the file when it is moved.
- One project \leftrightarrow one org location.  Overlay-bound projects are excluded from mirror sync; unbound projects keep their mirror files. Migration is project by project.
- Directory roots extend the category tree: the path =Home/garden/plants.org= can project to project Home › sub-project Garden.  Default: file = project.

** Identity

- *One ID by default.*  The Todoist ID stays in =:ID:=, as today.  Nothing to migrate for existing tasks, and =[[id:…]]= links and ID-derived org-attach folders (=data/6X/…=) keep working, because org-id resolves any =:ID:= value.
- *Exception.*  A heading that already has an org-id keeps it, and its Todoist ID goes in =TODOIST_ID=.  This happens when an existing notes heading becomes a task or a container (other notes link to it, its attachment folder derives from it), or when a task got an org-id before its first push.  Overwriting the org-id breaks every link to it (row 16).  Rewriting all links across files is the alternative, but it cannot reach links outside org files.
- *Lookup.*  =TODOIST_ID= if present, else a dash-free =:ID:=.  Todoist IDs never contain a dash; org-id UUIDs always do.
- Global index Todoist ID \to marker across overlay files and their archive files, built from property drawers.
- Copying a subtree duplicates its properties.  A Todoist ID found twice is quarantined: neither heading syncs until the user keeps one and removes the ID from the other.

** Minimal footprint

Overlay stores one ID per linked heading (=:ID:=, or =TODOIST_ID= for the exception), plus properties the user actually reads (=ASSIGNEE=).  Order, recurrence string, section flags and comment IDs live in the state store, keeping notes files readable.

** Scope — which headings are exposed

- Candidate: a heading with a TODO keyword inside a bound file.
- Excluded, with inheritance: tag =noTodoist= (configurable), =COMMENT= headings, =ARCHIVE=-tagged subtrees, property =TODOIST: ignore=.
- DONE headings without a Todoist ID are never pushed; history stays local.  Only state transitions on linked tasks sync.
- Keywords: todo-type \to unchecked, DONE \to completed, CANCELED \to configurable (complete with a label, or delete from Todoist while the heading stays CANCELED in org). Non-default todo keywords (STARTED, WAITING) can surface as labels so the phone shows them.
- Tags \leftrightarrow labels: only local (non-inherited) tags that are listed in =orgist-overlay-label-tags= or already exist as Todoist labels. =#+FILETAGS= and inherited tags never become labels.
- Open: habits (=STYLE: habit=) excluded by default?

** Projection — org tree to Todoist

Every exposed task appears, wherever it sits, including tasks at the top level of the file.  Non-task headings appear only when a task sits below them; a notes heading with no task below it never appears.  The category tree surfaces lazily.

| Org                            | Todoist (default)                       |
|--------------------------------+-----------------------------------------|
| bound file                     | project                                 |
| top-level task                 | task in the project, no section         |
| level-1 container              | section                                 |
| deeper container               | uncompletable header task (=* = prefix) |
| task under a container         | task under that container's projection  |
| task under task                | sub-task                                |
| non-task heading inside a task | part of the task's description          |

- *Flatten alternative.*  Deep containers become section names ("Garden › Irrigation"): fewer header tasks, more sections, and the 20-section limit arrives sooner.  Chosen per file.
- *Overrides.*  =TODOIST_AS= = =project= | =section= | =header= | =flatten= | =transparent=.  =TODOIST_PROJECT_ID= on a subtree routes it to another project, e.g. private tasks inside a file bound to a shared project.
- *Limits.*  Depth beyond the sub-task limit flattens the deepest levels. Before pushing, the projection counts active tasks and sections per project and refuses, with an explanation, to exceed 300 or 20.
- *Structural diff.*  The projection is recomputed each scan and diffed against the previous one, stored in state.  The result is =section_add= / =section_update= / =section_archive=, =item_move=, and header add/remove. Renaming a notes container renames its section.  A section orgist created that loses its last task is archived.
- *Breadcrumb.*  Optionally append the org path to the description, so the phone shows context for flattened or header placements.

** Inbound — Todoist to org

- *Field updates* on linked tasks: three-way merge per field, with the snapshot as base.  If only one side changed, take it.  If both changed differently, org wins; the remote value goes into a logbook note and the review buffer.
- *Echo suppression* for lossy fields: the snapshot records both the org source and the rendered value last sent.  A remote value equal to the last rendered one is no change, so the org source stays.  This protects titles with org links or markup, and anything pandoc cannot round-trip.
- *Description* — the task's body syncs both ways, as today.  The body is everything in the task's subtree except its child tasks: text plus any non-task child headings.  Child headings become Markdown headings in the description, levels relative to the task (a =****= heading under a level-3 task \to =#=), so the phone shows them as sub-titles; on pull they become child headings again, as today.  Today's rule stops at the first child heading (row 17); overlay, and the M0 fix for mirror, extend it to the whole subtree.  Inbound edits use the same three-way merge and echo suppression, so org markup that pandoc cannot round-trip is not replaced by its rendered form.  A body over Todoist's 16 383-character limit is not pushed, and review explains why.  =orgist-clear-body= gives way to a merge that only touches the description region, never child tasks.
- *Private bodies, per project* — =orgist-overlay-description= set to =none= keeps bodies local, e.g. for a shared project whose collaborators should see tasks but not the notes inside them.
- *New remote task* — inserted under the heading bound to its parent or section.  With no binding it goes to the file's landing zone (default =* Inbox=, created on demand).  Todoist Inbox tasks go to =orgist-overlay-inbox-file=.
- *Remote move* — within the project, refile under the bound heading; across projects, refile across files.  Both are journaled and reviewed by default.
- *Remote deletion* — delete means delete: the heading and its whole subtree are removed, as today.  The removal goes through the destruction journal and the cycle's history commit, so it is recoverable, never silent.
- *Remote reorder* — applied only within runs of adjacent task siblings; a task never moves across a notes heading.  Container order is org-owned.
- *Remote rename of a section or project* — the container is org-owned, so it goes to review: accept renames the heading, reject pushes the org name back.
- *Review* — inbound structural changes (move, deletion, rename, field conflict) go through org-sync-confirm in =ask= mode.  Today it reviews only outbound changes.

** Outbound — org to Todoist

- A new TODO in scope \to =item_add=, placed by the projection; missing containers are created first.
- A refile within scope \to =item_move=.  A refile into a file outside scope \to =item_delete=: the task leaves the view, the heading stays where it was refiled.
- *Moves are not deletions.*  Before an =item_delete=, a missing ID is looked up in the other overlay files, archive files and =org-id-locations=, so a refile or an archive is recognized as such.  Truly gone \to =item_delete=.
- =org-archive-subtree=: archive files are indexed.  Archiving a DONE task is a no-op; archiving a TODO asks whether to complete it or delete it from Todoist.
- Logbook notes added after linking \to =note_add=.  Notes already present at link time are the baseline and are never pushed.
- Attachments: task headings (and their non-task children, as today), never notes outside tasks.

** Apply inbound edits in-process

For overlay files, remote changes are applied to live buffers in the main Emacs: when a file is open, its buffer is the truth.  The subprocess only fetches and converts (network, pandoc) and returns an edit list.  That removes hazard 10: no disk write races an open, modified notes buffer.

All buffer mutation goes through a small set of guarded primitives: set field, merge description, insert heading, refile, journaled delete. These are the only code paths the blast-radius guards and journal need to cover.

** Staging — projection-only first

A useful first overlay is push-only projection, plus inbound completion and comments.  Todoist becomes a view you can check off (phone, collaborators), and inbound title or date edits arrive as review items.  This exercises binding, identity, scope, projection and the safety net with little inbound risk.  Full inbound follows once a pilot runs clean.

* Multiple machines

Today each machine has its own mirror files and state, and Todoist is the hub every machine converges on.  Overlay files are shared by every machine — over SMB today, through NextCloud later — and that changes what is safe.

With per-machine snapshots, stamps and token, two failures appear on either transport:

- Machine B sees A's inbound writes as local edits and pushes them back. That is mostly idempotent, but B's three-way merges run against the wrong base and turn into reverts when a collaborator edited in between.
- A stale buffer on B with unsaved edits, saved after A's pull, overwrites A's changes while A's state records them as applied.  The resulting drift is pushed back as reverts.

The two transports differ in what they offer against this:

|                                | SMB (today)                                    | NextCloud (later)                                 |
|--------------------------------+------------------------------------------------+---------------------------------------------------|
| Copies of a file               | one, on the server                             | one per machine, synced asynchronously            |
| Cross-machine atomic operation | yes (=make-directory=)                           | none: lock and state files propagate with a delay |
| Concurrent writes to one file  | last save wins (Emacs warns on a stale buffer) | a "conflicted copy" file next to the original     |

| Option                              | SMB        | NextCloud                           | Notes                                                          |
|-------------------------------------+------------+-------------------------------------+----------------------------------------------------------------|
| 1. Every machine syncs, coordinated | lock works | no lock; only the reconcile variant | no extra machine                                               |
| 2. Dedicated sync machine           | works      | works                               | single Todoist writer; needs a review channel                  |
| 3. NextCloud server-side plugin     | —          | works                               | always on, next to the canonical files; org handling rewritten |

*Option 1.*  Over SMB, a lock (atomic =make-directory= holding host, pid and expiry, with a heartbeat, held for one pull + push cycle) plus shared state works.  Over NextCloud neither exists, so the only variant is to reconcile instead of lock: store the sync base in the file itself (a per-heading hash of the last-synced fields) so base and content always travel together, and make commands deterministic (command =uuid= and =temp_id= derived from the heading ID and content) so two machines pushing the same change produce one effect.  That depends on Todoist deduplicating repeated command UUIDs across clients (to verify), and it still leaves conflicted copies.

*Option 3.*  A NextCloud app is PHP: org parsing, editing and the Todoist mapping would be reimplemented outside Emacs, duplicating orgist without org-mode's own parser.  Its real advantage is location: always on, next to the canonical files.  If NextCloud should also expose tasks (its Tasks app speaks CalDAV VTODO), that is a second projection target beside Todoist, so the projection layer should not assume Todoist (see Backend independence).

*Recommendation — option 2, placed server-side.*  A headless Emacs sync worker runs next to the file store and is the only Todoist writer.  On SMB it works on the share directly; on NextCloud it is woken by file-change events and writes through NextCloud (WebDAV, or =occ files:scan= after a direct write) so clients see its changes.  This takes option 3's location without rewriting orgist, works on both transports, keeps working while laptops are offline, and needs no cross-machine lock.  Desktops keep editing and reviewing: the worker publishes pending changes, outbound and inbound, as data; org-sync-confirm renders them in Emacs; approvals go back as data.

Whatever the option, NextCloud makes the sync writer one more editor of the files: a human edit on a laptop concurrent with a sync write produces a conflicted copy.  Keep sync writes small and quick, detect conflicted copies, and merge them by heading ID (three-way, with the history commit as base) — useful beyond orgist.

Constraints that hold for every option:

- State keyed by root-relative paths, never absolute: =C:/…=, =Z:/…= and =/Users/…= name the same file on different machines.
- A machine whose buffer is modified *and* stale (file changed on disk) must not sync that file, and must warn: that is the lost-update window.
- Buffers of overlay files use auto-revert and keep the file's coding system (=utf-8-unix=); Windows must not introduce CRLF into shared files.
- When the file store is unreachable, overlay sync pauses; mirror projects are unaffected.

* Adoption — collapsing a mirror file into a notes file

=M-x orgist-overlay-adopt= takes a project and a target notes file:

1. Commit both files to history; require no pending write-back.
2. Match containers (sub-projects, sections) to notes headings by normalized title.  Unmatched containers get a new heading or a manual mapping.
3. Review a plan in org-sync-confirm:
   - container mapping and the destination of each task subtree;
   - DONE history: into the notes file, its =_archive= file, or left in the retired mirror file;
   - attachment relocation;
   - property migration: tasks keep =:ID:= (it already holds the Todoist ID); containers matched to headings that have an org-id get =TODOIST_ID=; =TODOIST-ORDER=, =TODOIST_DUE_STRING= and =SECTION= move into state.
4. Apply.
5. Verify round-trip identity: a pull changes no buffer and a diff scan emits zero commands.  Otherwise roll back automatically from history.
6. Retire the mirror file to =<base>/retired/=, excluded from mirror sync. It is never deleted.

=orgist-overlay-detach= reverses it: the file stops syncing (tasks stay in Todoist), or a mirror file is rematerialized.

Pilot order: synthetic fixture \to test project \to a small unshared project \to larger projects \to shared projects last, since collaborators see every mistake.

* Backend independence

Nothing in the overlay core is Todoist-specific: the safety net, scope, identity, projection, three-way merge, the server-side worker and review would serve a CalDAV backend (VTODO, e.g. Nextcloud with Tasks.org on the phone) unchanged.  Todoist sits behind a backend interface from [[id:c6b4f748-2dab-4955-bdc9-34154b4b5268][M1 — Seams refactor]] on.

A CalDAV backend removes several Todoist constraints and changes a few rules:

| Concern                    | Todoist                                          | CalDAV (VTODO)                                                                                   |
|----------------------------+--------------------------------------------------+--------------------------------------------------------------------------------------------------|
| Identity                   | server assigns IDs; temp-id remap after =item_add= | the client chooses the =UID=: the org-id itself, no remap, no second property                      |
| Concurrency                | none per item                                    | =ETag= with =If-Match=: a stale write fails instead of overwriting the phone's edit                  |
| Incremental sync           | sync token                                       | =sync-collection= REPORT (RFC 6578)                                                                |
| States                     | checked or unchecked                             | =NEEDS-ACTION=, =IN-PROCESS=, =COMPLETED=, =CANCELLED=                                                   |
| Dates                      | due, deadline                                    | start (=DTSTART=) and due (=DUE=): a home for both SCHEDULED and DEADLINE                            |
| Limits                     | 300 tasks and 20 sections per project            | none per list                                                                                    |
| Structure                  | projects, sections, sub-tasks                    | lists (calendars) and =RELATED-TO= parents; no sections                                            |
| Containers                 | sections, uncompletable header tasks             | categories (tags) or parent tasks; no uncompletable tasks                                        |
| Description                | Markdown                                         | plain text; Tasks.org renders Markdown when enabled                                              |
| Comments                   | first-class                                      | =COMMENT= property; client support varies                                                          |
| Fields orgist does not map | dropped by the API                               | kept: patch the server's copy of each task, never regenerate it                                  |
| Moves                      | =item_move=                                        | between lists: removed from one, added to another with the same =UID=; must not read as a deletion |

Tasks.org rewrites tasks after importing them; one report saw subtask links broken by those writes on several servers.  Verify that the hierarchy round-trips on a throwaway list before relying on it.

Sources: [[https://tasks.org/docs/markdown/][Tasks.org Markdown]], [[https://github.com/tasks/tasks/issues/3023][tasks/tasks#3023]].

* Other ideas

- *Query views.*  A Todoist project defined by a query, e.g. every TODO tagged =:errand:= across files.  A task has exactly one Todoist home, so views must partition (first match wins).  A later phase, but the projection code should not preclude it.
- *Capture anywhere, organize in org.*  Phone captures land in the inbox; refiling in org moves the task in Todoist.
- *Privacy boundary.*  In a shared project the projection is exactly what collaborators see: tasks with their bodies, never notes outside tasks.  The per-project =none= description policy and per-subtree routing cover tasks whose bodies should stay private.
- *=orgist-doctor=.*  Duplicates, orphans, TODOs in scope not yet pushed, limit headroom per project, lock holder, history size, last cycle outcome.
- *One review library.*  All review stays in org-sync-confirm: the single place to review, select and approve what gets sent to a remote, for orgist and ejira alike.  Overlay adds two needs there: reviewing inbound changes before they are applied, and reviewing a queue produced by another process (the sync worker), which means review items must be describable as data rather than closures.  Whether history, journal, guards and projection also move into a library shared with ejira stays open; decide before [[id:c6b4f748-2dab-4955-bdc9-34154b4b5268][M1 — Seams refactor]].
- *Agenda.*  Once a project is adopted its tasks appear once, from the notes file.

* Testing strategy

- *Content preservation.*  Property test: a synthetic notes fixture receives random sequences of remote events (update, move, delete, complete, reorder, description edit).  After every pull, all notes outside tasks are preserved as a multiset of lines, apart from journaled removals, and task bodies change only in the fields the events touched.
- *Blast radius.*  Each event changes only its declared region.
- *Round-trip identity* after adoption: pull \to no buffer change; diff \to zero commands.
- *Projection.*  Deterministic output, limit enforcement, structural diffs for renames and moves.
- *Multiple machines.*  A worker process and an editor process on one shared directory: concurrent edits and pulls lose nothing, each change is pushed exactly once, and a forced conflicted copy merges by heading.
- *Mirror regression.*  Every existing suite stays green through [[id:b07d5ba5-76ed-4069-8058-c02f3806a57b][M0 — Safety net]] and [[id:c6b4f748-2dab-4955-bdc9-34154b4b5268][M1 — Seams refactor]].
- Fixtures are synthetic only (public repository).

* Open questions

Each with the current recommendation.

1. Mode names — /mirror/ and /overlay/.
2. Task bodies — decided: synced as today, extended to non-task child headings; =none= per project for private bodies.
3. Identity — decided: the Todoist ID stays in =:ID:=; =TODOIST_ID= only for headings that already have an org-id.
4. Remote deletion — decided: delete means delete, on both sides; the journal and history make every deletion recoverable.
5. Deep containers — header tasks; flatten per file.
6. Multiple machines — a server-side sync worker (option 2 placed next to the file store); an SMB lock only as a stepping stone before NextCloud.
7. DONE history on adoption — the notes file's =_archive= file.
8. Inbound reorder — only within adjacent task runs.
9. Review — decided: org-sync-confirm is the one review library.  Open: share history, journal, guards and projection with ejira; decide before [[id:c6b4f748-2dab-4955-bdc9-34154b4b5268][M1 — Seams refactor]].

Found while scoping it: the sync, completed-tasks and comments subprocesses all save org files behind Emacs (with the "changed on disk" check disabled), so a file saved while one runs is overwritten, and a write-back made meanwhile loses its snapshot updates when the subprocess's snapshot file is reloaded.  The user chose Emacs as the only writer, to be tried in daily use before it becomes the default:
   - Subprocesses return the snapshot entries they changed; Emacs merges them field by field instead of reloading the file (all modes).
   - =orgist-sole-writer= (default off): a subprocess works on a staged copy of the project files.  Emacs then compares, per file, the copy, the subprocess's result and the live buffer or file.  A file nobody touched takes the result; a file edited or saved meanwhile is left alone, with its snapshot changes dropped and the sync cursors (sync token, completed-tasks timestamp, comments flags) held back, so the next sync redoes those changes against the edited text.  Emacs never re-applies a sync on the spot, which keeps it responsive; the log reports what was swapped, what was deferred and how long Emacs was busy.

Verified: a full sync response fetched once from the real account and replayed offline into two copies of the real mirror, with the code before and after M1, produced byte-identical files, snapshots and labels.  =orgist-sole-writer= stays off until it has been tried in daily use: on the real data a run that changes nothing keeps Emacs busy about 95 ms, and taking over the largest file about 135 ms.
